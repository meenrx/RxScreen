# RxScreen (On-Prem) — คู่มือเชื่อมต่อฐานข้อมูล รพ. + หลักประกันสำหรับ IT

ระบบคัดกรองใบสั่งยาผู้ป่วยใน ที่ทำงาน **ในเครื่อง (localhost/LAN)** อ่านข้อมูลจาก
HOSxP แบบ **อ่านอย่างเดียว** และ **ไม่ส่งข้อมูลออกภายนอก** โดยเก็บข้อมูลส่วนบุคคล
ให้น้อยที่สุดตามหลัก PDPA (อย่างมากแค่ **AN, HN** + ข้อมูลที่จำเป็นต่อการคัดกรอง)

> เอกสารในโฟลเดอร์นี้:
> - `README.md` — ภาพรวม + สิ่งที่ต้องระบุ + หลักประกันสำหรับ IT (ไฟล์นี้)
> - `.env.hospital.example` — **แบบฟอร์มค่าเชื่อมต่อให้ IT กรอก**
> - `hosxp_readonly.sql` — user **อ่านอย่างเดียว** ของ HOSxP + view เฉพาะคอลัมน์คัดกรอง
> - `rxscreen_db.sql` — **ฐานข้อมูลกลางของ RxScreen เอง** (เก็บผลคัดกรอง/intervention) แยกจาก HOSxP → ทุกเครื่องบันทึก/ดูได้

> **ที่เก็บผลคัดกรอง:** ถ้าใช้เครื่องเดียว → sqlite ในเครื่องพอ · ถ้าต้องการให้ **ทุกเครื่องเห็นข้อมูลเดียวกัน** → ใช้ฐานกลาง `rxscreen` (ดู `rxscreen_db.sql`) — RxScreen เขียนเฉพาะฐานนี้ HOSxP ยัง read-only เสมอ

## 1. สถาปัตยกรรม (ทุกอย่างอยู่ในเครื่อง/ใน รพ.)

```
[HOSxP MySQL/MariaDB]  --(อ่านอย่างเดียว, user เฉพาะ, ผ่าน VIEW)-->  [RxScreen backend ในเครื่อง]
      (ของ รพ.)                                                          |  (Node บน localhost)
                                                                        v
                                                             [เบราว์เซอร์เภสัชกร ในเครื่อง]
                                                             + rules engine คัดกรอง (offline)
                                                             + ผลคัดกรองเก็บใน sqlite ในเครื่อง

  ❌ ไม่มีการต่อออกอินเทอร์เน็ต   ❌ ไม่มีคลาวด์   ❌ ไม่เขียนกลับ HOSxP
```

- **Backend ในเครื่อง**: query HOSxP ด้วย SELECT ที่ผูกพารามิเตอร์ (AN) แล้วคืนเฉพาะฟิลด์ที่ใช้คัดกรอง
- **Rules engine ทำงาน offline อยู่แล้ว** (DDI, ไต, แล็บ×ยา, HAD, ขนาดยาเด็ก, RDU) — ไม่ต้องพึ่งบริการภายนอก
- **ตัดส่วนคลาวด์ออก**: เวอร์ชัน on-prem จะปิด Firebase (Auth/Firestore/Hosting) และ AI ภายนอก → ใช้ล็อกอินในเครื่อง + เก็บผลใน sqlite แทน

## 2. ข้อมูลที่ระบบเข้าถึง (ขอบเขต PDPA)

| ต้องใช้ (เพื่อคัดกรอง) | ✅ | **ไม่แตะเด็ดขาด** | ❌ |
|---|---|---|---|
| AN, HN (คีย์เชื่อมข้อมูล) | ✅ | ชื่อ-นามสกุล | ❌ |
| คำสั่งใช้ยาของแพทย์ (generic, ขนาด, วิธีใช้) | ✅ | เลขบัตรประชาชน | ❌ |
| ผลแลปที่เกี่ยวข้อง (ไต/ตับ/เกลือแร่/INR ฯลฯ) | ✅ | ที่อยู่ / เบอร์โทร | ❌ |
| ประวัติแพ้ยา | ✅ | สิทธิการรักษา/การเงิน | ❌ |
| ประวัติยาย้อนหลัง (คัดกรองซ้ำซ้อน/ปฏิกิริยา) | ✅ | ข้อมูลญาติ/ผู้ติดต่อ | ❌ |
| Dx ที่เกี่ยวข้อง (CKD, ตั้งครรภ์, ตับ) | ✅ | เวชระเบียนส่วนที่ไม่เกี่ยวยา | ❌ |

> เทคนิคคุมขอบเขต: **เปิดเผยผ่าน VIEW** ที่มีเฉพาะคอลัมน์ข้างต้น แล้ว grant สิทธิ์เฉพาะ view
> (ดู `hosxp_readonly.sql`) → แม้แต่ระบบก็ **มองไม่เห็น** คอลัมน์ PDPA อื่น

## 3. สิ่งที่ต้องระบุ/ตกลงกับ IT (Checklist)

**ฐานข้อมูล**
- [ ] ชี้ไปฐานไหน — แนะนำ **replica / report DB** (ไม่รบกวน production หลัก)
- [ ] Host/IP, Port (3306), ชื่อฐาน (เช่น `hos`)
- [ ] charset = **tis620**, timezone = +07:00 (HOSxP ภาษาไทย)
- [ ] เวอร์ชัน HOSxP / โครงสร้างตาราง (ยืนยันชื่อคอลัมน์ใน view ให้ตรง)

**ขอบเขต/ตรรกะ**
- [ ] คีย์ค้นหา = **AN** (หรือ HN) เท่านั้น — ไม่ค้นด้วยชื่อ
- [ ] วอร์ดที่คัดกรอง / ช่วงเวลาแลป (เช่น 90 วัน) / ประวัติยา (เช่น 180 วัน)
- [ ] map generic_name ของยา และชื่อผลแลป ให้ตรงศัพท์ รพ.

**เครือข่าย/ความปลอดภัย**
- [ ] เครื่อง/IP ที่จะรัน RxScreen (ใช้จำกัด host ของ DB user)
- [ ] Firewall: เปิด port MySQL **เฉพาะจาก IP เครื่องนั้น** ไปยัง DB
- [ ] ยืนยัน "ไม่เปิดทางออกอินเทอร์เน็ต" ให้เครื่องนี้ (air-gap ได้)

**ผู้ใช้งาน/บันทึก**
- [ ] วิธีล็อกอินเภสัช (PIN ในเครื่อง / LDAP ภายใน) — ไม่ใช้บัญชีคลาวด์
- [ ] ที่เก็บผลคัดกรอง (sqlite ในเครื่อง) + ระยะเก็บ (retention)
- [ ] NTP/time sync (ให้ timestamp ตรง)

## 4. หลักประกันสำหรับ IT (ทำไมปลอดภัยต่อ HOSxP)

1. **อ่านอย่างเดียวจริง** — DB user มีสิทธิ์ `SELECT` เท่านั้น ตรวจได้ด้วย `SHOW GRANTS`
   ไม่มี INSERT/UPDATE/DELETE/DDL → **แก้/ลบข้อมูล HOSxP ไม่ได้เลย**
2. **เห็นเฉพาะที่อนุญาต** — grant บน **VIEW** ที่ IT สร้าง/ตรวจเอง → ระบบมองไม่เห็นคอลัมน์อื่น
3. **ไม่เขียนกลับ HOSxP** — ผลคัดกรอง/บันทึกการแทรกแซง เก็บใน sqlite **แยกในเครื่อง**
4. **รันในเครื่อง ไม่ออกภายนอก** — bind `127.0.0.1`/LAN, ไม่มี egress ออกเน็ต, ทำงานแบบ air-gap ได้
5. **PDPA ขั้นต่ำ** — ดึงแค่ AN/HN + ข้อมูลคัดกรอง; ไม่แตะ ชื่อ/ที่อยู่/บัตร ปชช./เบอร์โทร
6. **ยกเลิกได้ทันที** — `DROP USER` / `REVOKE` แล้วระบบหยุดอ่านทันที **โดยไม่กระทบ HOSxP**
7. **ตรวจสอบได้** — เก็บ log ทุก query ในเครื่อง; ส่งรายการ query ทั้งหมดให้ IT review ก่อนเปิดใช้
8. **ไม่เพิ่มภาระฐาน** — query เบา ค้นด้วย AN (มี index), จำกัดจำนวน connection + query timeout,
   และแนะนำให้ชี้ไป replica → **ไม่ล็อกตาราง ไม่กระทบงานเวชระเบียน/ห้องยา**

> ข้อ 1–3 คือหัวใจ: **ระบบนี้ "อ่าน" ได้อย่างเดียว และมองเห็นได้เฉพาะคอลัมน์ที่ IT เปิดให้**
> ต่อให้ระบบมีบั๊กหรือถูกบุกรุก ก็ไม่สามารถเปลี่ยนแปลงข้อมูลใน HOSxP ได้

---

## 5. ขั้นตอนเปิดใช้ (สรุป)

1. IT กรอก `.env.hospital.example` → บันทึกเป็น `.env.hospital` (เก็บในเครื่อง)
2. DBA รัน `hosxp_readonly.sql` (ปรับชื่อฐาน/คอลัมน์/IP ให้ตรง) → ได้ user + view
3. ตั้ง firewall เปิด port MySQL เฉพาะ IP เครื่อง RxScreen
4. รัน backend + เปิดเบราว์เซอร์ในเครื่อง → ทดสอบดึง 1 AN → ตรวจ log query กับ IT
5. เปิดใช้จริงกับเภสัชกร

---

## 6. งานพัฒนาที่ต้องทำ (จาก cloud → on-prem)

- เพิ่ม **local backend** (Node/Express) + connector MySQL (อ่านอย่างเดียว) อ่าน view
- map ผล query → รูปแบบ `PatientInput`/`DrugEntry` ที่ rules engine ใช้อยู่
- ปิด/ถอด Firebase + AI ภายนอก, เปลี่ยนล็อกอินเป็น local, เก็บผลลง sqlite
- แพ็กเป็นตัวรันในเครื่อง (เช่น service/exe) พร้อมสคริปต์ติดตั้ง

> Rules engine, UI คัดกรอง, ตัวคำนวณไต/ขนาดยาเด็ก/HAD ใช้ของเดิมได้ทั้งหมด (offline อยู่แล้ว)
